# Python `ml_pipeline` スナップショット管理方針

| 項目 | 内容 |
|------|------|
| 版 | 0.1 |
| ステータス | 採用（チーム合意済みの前提） |
| 目的 | 上流 `algo_trader_v1/ml_pipeline` の変化に依存せず、**再現可能な学習・評価**と **Rust 契約（ONNX / `feature_schema`）** を同一リポジトリで固定する。 |

---

## 1. 背景とトレードオフ

- **上流**（`algo_trader_v1`）は今後も変更される。  
- **本リポ**（`algo_trader_rust`）では、互換性検証と CI の安定のため、**現時点の Python コードをコピーして管理**する。  
- **二重管理**により、バグ修正・セキュリティパッチが片側にしか入らないリスクがある — 本書で **運用ルール**で緩和する。

---

## 2. 配置規約

### 2.1 ディレクトリ名

次のいずれかとし、**無印の `ml_pipeline/` 単体は避ける**（上流と同一視されやすいため）。

| 形式 | 例 |
|------|-----|
| 日付付きスナップショット | `vendor/ml_pipeline_snapshot_2026-04-12/` |
| 版＋日付 | `vendor/ml_pipeline_v0.1_2026-04-12/` |

新規スナップショットを追加するときは **別ディレクトリ**とし、旧版は削除せず **一定期間併存**してよい（比較実験用）。

### 2.2 含めてよいもの・避けるもの

| 含める | 避ける・gitignore |
|--------|---------------------|
| ソース（`.py`）、`requirements` または `pyproject`、スクリプト | **実 `.env`**、本番 URL・トークンが書かれたファイル |
| ドキュメント・設定テンプレート（`.env.example` はマスク済みなら可） | 巨大な **生データ**（必要なら LFS または別ストア） |
| テスト・CI 用の最小フィクスチャ | `__pycache__/`, `.venv/`, `*.pyc` |

`algo_trader_rust/.gitignore` に `vendor/**/.venv/` 等を追加する。

## 3. 上流との関係

| 概念 | 定義 |
|------|------|
| **上流（canonical 開発）** | `algo_trader_v1/ml_pipeline` — 新機能・本番修正の主戦場。 |
| **本リポのスナップショット** | **検証・再現・Rust 連携の固定点**。上流の「その時点の写し」。 |

- スナップショットは **上流の置き換えではない**。  
- 意図的に更新する場合のみ、上流から **手動マージ**または **git subtree / submodule**（§4）で取り込む。

---

## 4. 同期方式（推奨度）

| 方式 | 利点 | 欠点 |
|------|------|------|
| **手動コピー + README 記録** | 単純 | 差分追跡が弱い |
| **git subtree** | 単一リポに履歴を取り込める | 初回設定がやや複雑 |
| **git submodule**（上流を別リポ／パス固定） | 上流コミット ID が明確 | クローン手順が増える |

チーム運用に合わせて一つに決める。**最低限**、スナップショット直下の `README.md` に **由来**（上流リポ URL・コミットハッシュ・コピー日）を書く。

---

## 5. Rust との契約（互換の単一ソース）

二重管理の害を減らすため、**Rust と共有する契約**は次に限定する。

1. **`feature_schema.json`** の `version` と列順  
2. **ONNX** の入出力名・形状（`strategies-predict` と一致）  
3. （任意）学習出力の **モデル ID / アーティファクト ID** を [design-unmet-capabilities-2026-04-12.md](design-unmet-capabilities-2026-04-12.md) のトレーサビリティ方針に合わせる  

**CI:** スナップショット内スクリプトで生成した ONNX を用い、`cargo test -p strategies-predict` のスモークと突合する（既存 `onnx_smoke` を拡張してよい）。

---

## 6. 更新ポリシー（例）

- **トリガー:** 上流で破壊的変更、または Rust 側でスキーマバンプが必要になったとき。  
- **手順（案）:**  
  1. 上流でタグまたはコミットを決める。  
  2. 新ディレクトリ `vendor/ml_pipeline_snapshot_YYYY-MM-DD/` に取り込む。  
  3. `spec/ml-bridge.md` と本書の「現行スナップショット」欄を更新。  
  4. CI 通過を確認。  
  5. 旧スナップショットの削除は **1 リリース遅延**してよい。
